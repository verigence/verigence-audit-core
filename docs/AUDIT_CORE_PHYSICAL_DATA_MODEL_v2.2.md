> This document defines the logical/physical-model delta required by UC02. Existing VAC-DM-002 tables remain authoritative unless explicitly changed below. No SQL, migration or runtime database privilege is changed by this Markdown document.

---

## 1. Existing hierarchy retained

The existing v2.1 hierarchy is unchanged:

```text
projects (PK = tenant_id)
  -> dealers
      -> dealer_outlets
          -> customers
              -> journeys
```

`tenant_id` remains the canonical Security Tenant/Audit Project key on Project-owned data.

UC02 adds Project administration/reliability records and Project-effective Product Master versioning. It does not create a second Project UUID below Security Tenant.

---

## 2. Project table usage

Existing `projects` remains the business projection of the Security Tenant.

The UC02 Project Details UI uses existing/approved Project fields including:

```text
project_name
oem_id
product_category_id
effective_start_date
effective_end_date
timezone_name
region_code
project_status
```

No `tenant_code` is added to Audit Core for UI purposes. Security owns its internal Tenant Code.

Post-activation mutability is enforced in application/domain logic with Audit Core audit history:

Editable after dependencies exist:

- project name;
- effective end date;
- timezone;
- region/geography.

Restricted after operational Journey/dependent published-master use:

- OEM;
- product category;
- effective start date.

## 3. Dealer and Dealer Outlet

### 3.1 Dealer

Existing Dealer structure is retained.

No latitude/longitude columns are added to Dealer for UC02.

Existing internal Dealer Code remains but is generated by Audit Core rather than required from the frontend.

### 3.2 Dealer Outlet

Existing Outlet address/location fields are retained, including the current physical-model fields for address/city/state/postal code and latitude/longitude.

Add one nullable enrichment field conceptually:

```text
dealer_outlets.google_place_id  nullable string
```

Rules:

- nullable;
- not part of PK/unique business identity;
- no requirement that every Outlet has it;
- latitude/longitude also remain optional for UC02 manual-address path;
- Outlet identity remains the immutable Outlet ID, not the Google Place ID/address.

Existing internal Outlet Code remains but is server-generated rather than browser supplied.

---

## 4. Business assignments reused for Role Mapping

The existing `business_assignments` model remains the Audit Core authority for Project/Dealer/Outlet scope.

UC02 uses existing nullability/hierarchy semantics:

```text
Project-wide
  dealer_id = NULL
  outlet_id = NULL

Dealer-wide
  dealer_id = <dealer>
  outlet_id = NULL

Outlet-specific
  dealer_id = <dealer>
  outlet_id = <outlet>
```

A Role Mapping may therefore materialize multiple active assignment rows for one USER when the requested scope contains multiple Dealers or Outlets.

No independent `project_employees` table is added in Phase 1.

Security operating-role assignment remains the persisted Tenant role. Audit Core business assignments store only Audit Core business scope.

### 4.1 Role-to-scope validity

Application invariants:

- PC rows are Outlet-specific;
- TL rows are Dealer-wide;
- PM is Project-wide;
- CRM is Dealer-wide or Project-wide;
- Executive is Project-wide.

Every ACTIVE Outlet having at least one ACTIVE PC mapping is evaluated by Project Readiness; it is not implemented as a static FK/cardinality constraint because mappings can change administratively.

## 5. Administrative operation store

UC02 needs durable orchestration that survives retry/browser refresh and, for deletion, survives removal of the Project itself.

Add a platform-administrative operation concept outside the ordinary Tenant-owned delete cascade.

Conceptual table:

```text
administrative_operations
  operation_id uuid PK
  operation_type
      PROJECT_PROVISION
      ROLE_MAPPING
      PROJECT_DELETE
  tenant_id nullable
  idempotency_key
  semantic_request_hash
  status
      RECEIVED
      RUNNING
      RECOVERY_REQUIRED
      COMPLETED
      FAILED
  current_step nullable
  initiated_by_user_id
  correlation_id nullable
  safe_request_summary jsonb nullable
  security_receipt jsonb nullable
  audit_core_receipt jsonb nullable
  di_receipt jsonb nullable
  last_error_code nullable
  last_error_summary nullable
  created_at_utc
  updated_at_utc
  completed_at_utc nullable
```

Design rules:

- platform/admin table is not deleted merely because the target Project/Tenant row is deleted;
- `tenant_id` is stored as the target identifier but should not use a cascading FK that destroys the receipt on whole-Project deletion;
- one logical request/idempotency key cannot create duplicate destructive/provisioning operations;
- module receipts contain only safe state/correlation identifiers, never bearer tokens/secrets;
- exact JSON shape may be normalized into child tables during implementation if repository conventions require it; semantics above are mandatory.

No retention duration is invented here. Existing/approved Audit Core administrative-audit retention policy governs until a separate decision sets one.

---

## 6. Project provisioning operation

`PROJECT_PROVISION` uses `administrative_operations` to track:

```text
Security Tenant creation
 -> Audit Core Project projection
 -> DI Tenant/Project provisioning
```

The operation may exist before `tenant_id` is known; `tenant_id` is set after Security returns the canonical identity.

The operation must retain enough safe downstream receipt data to resume without creating another Tenant after a timeout.

No module credentials/tokens are persisted in this record.

---

## 7. Role Mapping composite operation

`ROLE_MAPPING` uses the same durable-operation mechanism when a Security role write and Audit Core assignment write cannot be completed as one transaction.

The authoritative end state remains:

```text
Security operating role
+
Audit Core business_assignments
```

The operation record exists only to reconcile partial cross-module administration; it is not a second source of truth for the mapping.

## 8. Project Master import/staging model

UC02 introduces a generic Audit Core staging layer for Excel-driven Project masters.

The staging layer does not replace the owning domain's authoritative version tables.

### 8.1 Import header

Conceptual table:

```text
project_master_imports
  import_id uuid PK
  tenant_id
  owner_module
  master_key
  effective_from date nullable according to descriptor
  template_version nullable
  original_file_name
  file_hash
  status
      UPLOADED
      PARSING
      PREVIEW_READY
      VALIDATION_FAILED
      CONFIRMED
      CANCELLED
      FAILED
  rows_parsed
  valid_rows
  warning_rows
  error_rows
  confirmed_version_id nullable
  created_by_user_id
  created_at_utc
  confirmed_by_user_id nullable
  confirmed_at_utc nullable
  version_no
```

For Audit Core effective-dated Excel masters, `effective_from` is mandatory before parse/confirm. It is never server-defaulted.

For a DI-owned import proxied through Audit Core, Audit Core may store only the proxy/operation receipt rather than duplicate DI staging rows. The owning-module data must not be copied into two authoritative stores.

### 8.2 Staged rows

For Audit Core-owned imports:

```text
project_master_import_rows
  tenant_id
  import_id
  row_number
  parsed_data jsonb
  validation_status
      VALID
      WARNING
      ERROR
  validation_messages jsonb/structured child records
  PRIMARY KEY (tenant_id, import_id, row_number)
```

`parsed_data` contains only the columns defined by the approved/versioned workbook template for that master. It is not a license to accept arbitrary JSON business fields.

### 8.3 File content

UC02 requires file hash/audit metadata and parsed preview. This design does **not** invent a new Audit Core binary-storage mechanism for retaining uploaded Excel bytes.

Whether the original workbook bytes are retained, and where, must reuse an approved platform storage mechanism or be explicitly designed before implementation. The staging database SHALL NOT silently add large binary workbook content without that decision.

### 8.4 Confirm

Confirm converts validated staging into the owning master domain's `DRAFT` version transactionally where possible.

After successful confirm, the authoritative master domain owns the version. Staging remains audit/reconciliation metadata according to approved retention.

## 10. Project Product Master — new effective version layer

### 10.1 Existing shared references remain

Current platform references remain:

```text
product_categories
oems
product_models
product_variants
colours
product_skus
```

They remain canonical stable identity/reference structures and are not made Project-owned by UC02.

### 10.2 New Project Product Master identity/version

Add a minimal Project-owned version layer conceptually:

```text
project_product_masters
  tenant_id
  product_master_id uuid
  status ACTIVE | INACTIVE
  created_at_utc
  PRIMARY KEY (tenant_id, product_master_id)
```

```text
project_product_master_versions
  tenant_id
  product_master_id
  version_id uuid
  version_no
  effective_from date
  lifecycle_status DRAFT | PUBLISHED | RETIRED
  source_import_id nullable
  published_by_user_id nullable
  published_at_utc nullable
  retired_by_user_id nullable
  retired_at_utc nullable
  created_by_user_id
  created_at_utc
  PRIMARY KEY (tenant_id, product_master_id, version_id)
```

Phase 1 permits effective-period overlap; no non-overlap exclusion constraint is added.

### 10.3 Version items

A Product Master version contains the set of canonical Product/SKU identities and an immutable Project-effective snapshot needed for reproducibility.

Conceptually:

```text
project_product_master_items
  tenant_id
  product_master_id
  version_id
  item_id uuid
  product_sku_id
  approved_product_snapshot jsonb
  source_import_row_no nullable
  PRIMARY KEY (tenant_id, product_master_id, version_id, item_id)
```

Rules:

- `product_sku_id` references the existing canonical Product SKU identity;
- `approved_product_snapshot` contains exactly the approved Product Master template fields/canonical product attributes for that row at confirmation time;
- the JSON snapshot is schema-validated against the versioned Product Master template and is immutable once the version is published;
- this document does not invent additional Product fields beyond the current product model/template;
- a confirmed import may create a genuinely new canonical product reference identity when the row represents a new approved product/SKU and the final canonical matching rules determine no existing identity matches;
- existing canonical IDs are never reinterpreted/mutated to mean a different Product simply to satisfy a new Project upload.

### 10.4 Journey reproducibility

The final implementation must ensure a Journey/evaluation can reproduce the Product/SKU meaning used at that time.

The preferred v2.2 direction is to retain an explicit `product_master_version_id` or equivalent immutable resolved reference/snapshot on the Journey/product evaluation path where Product Master context affects decisions.

The exact existing Journey-product table column placement must be chosen during DDL design after reviewing current `journey_products` and audit-evaluation references; this Markdown document does not invent a conflicting duplicate FK.

### 10.5 Price/Discount relationship

Price/Discount import validation must reject Product/SKU references that cannot be resolved against an applicable Project Product Master context.

Because Phase 1 explicitly allows overlapping Product Master effective periods, one remaining deterministic implementation rule must be approved before code: **when more than one PUBLISHED Product Master version is applicable to the same as-of date, which one is the resolver winner?**

This physical model deliberately does not invent that precedence.

## 11. Project Readiness persistence

Project Readiness is derived from authoritative module state and does not require a new authoritative readiness table in Phase 1.

Audit Core computes the view from:

- Project configuration;
- Dealer/Outlet state;
- business assignments;
- Security role/lifecycle information obtained through approved APIs;
- Project master states;
- DI provisioning/configuration readiness.

A cache/materialized projection may be added later only if needed; it is not part of this design.

## 12. Hard-delete model

### 12.1 Narrow delete

Dealer/Outlet delete first executes dependency queries inside the target Tenant.

No `ON DELETE CASCADE` should be introduced merely to make the UI Delete button succeed where operational descendants exist.

### 12.2 Whole-Project Audit Core delete graph

The implementation DDL/design review must enumerate the exact FK-safe deletion order for all Project-owned tables from VAC-DM-002 plus UC02 tables.

Logical categories include:

1. stop/reject new Project-scoped work;
2. delete/settle transient/admin staging and Project-owned operational rows in FK-safe child-to-parent order;
3. delete Customer/Journey/process/evidence projections/workflow/master/assignment/reference Project-owned rows as part of the explicitly confirmed whole-Project rollback;
4. delete Dealers/Outlets;
5. delete Project row;
6. retain `administrative_operations`/authoritative deletion receipt outside the cascade;
7. invoke Security Tenant deletion after Audit Core zero-state verification.

The exact table-by-table graph must be generated from the actual v2.2 DDL before migration review; this document does not guess FK ordering that can be mechanically derived from the approved schema.

### 12.3 Normal runtime role remains non-destructive

The v2.1 deployment rule that ordinary runtime business/audit execution should not have broad DELETE remains.

Phase-1 UC02 requires a separately controlled SuperAdmin administrative deletion path/DB privilege capable of the approved delete graph.

The exact PostgreSQL role/credential deployment is intentionally not fixed here because it is an implementation/deployment control, not an approved business rule. It must be least-privilege and inaccessible to normal PC/TL/PM/CRM/Executive request handling.

---

## 13. Audit trail and deletion receipt

Normal Audit Core business `audit_events` remains authoritative for live Project history.

Whole-Project deletion will remove Project-owned history where the Phase-1 rollback explicitly requires full cleanup. Therefore the cross-module administrative deletion receipt must be independent of the Project FK/cascade and retain only safe evidence sufficient to prove:

- operation ID;
- deleted Tenant/Project ID;
- initiating SuperAdmin USER ID/reference;
- module step outcomes/receipts;
- timestamps;
- final outcome/correlation.

No bearer token, raw document or secret is retained in that receipt.

---

## 14. Schema changes requiring later DDL work

No SQL is changed now. The later approved DDL/migration work will need to reconcile at minimum:

- nullable `dealer_outlets.google_place_id`;
- server-side Dealer/Outlet code generation behavior if any DB default/sequence is needed;
- `administrative_operations` or equivalent durable admin-operation store;
- Audit Core master import/staging structures;
- Project Product Master identity/version/item structures;
- any explicit Product Master version reference required for Journey/decision reproducibility;
- controlled administrative hard-delete DB privilege/path.

All changes must preserve Tenant isolation/RLS expectations or explicitly document why a platform administrative operation record sits outside Tenant-owned cascade/RLS behavior.

## 16. Review status and one unresolved resolver detail

The UC02 Product Master **scope** is resolved: Project-specific in Phase 1, reusable-existing option deferred to Phase 2.

One implementation-level business rule is still not present in the approved source decisions and is intentionally not invented:

> When overlapping PUBLISHED Product Master versions are both effective for the same as-of date in Phase 1, what is the deterministic Product Master version selection rule?

All other UC02 physical-model changes above follow the approved hierarchy, role/business-scope split, map optionality, Excel staging, hard-delete rollback and Project-specific Product Master decisions.
